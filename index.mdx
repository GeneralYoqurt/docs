**Frontend contract v1** (2026-09-17). Frontend produktu (web, studio, admin) rozmawia z self-hosted Supabase wyłącznie przez **RPC** i **Edge Functions**. Bank zadań to IP: student nie ma `SELECT` na `tasks` / `subtasks` ani LIST/SELECT na storage banku.

<Warning>
  Ten `openapi.yaml` jest ręczny. Operacje `live` są na `main`. Operacje `planned` są zatwierdzone do planowania FE — **nie** wołaj ich na `supabase-new` aż kod wejdzie. Playground jest w trybie prostym i **nie wysyła** żądań.
</Warning>

## Baza

| Warstwa | URL |
| --- | --- |
| API | `https://supabase-new.bioteach.pl` |
| RPC | `POST /rest/v1/rpc/{nazwa}` |
| Edge | `/functions/v1/{nazwa}` |
| Auth (GoTrue) | `/auth/v1` przez `supabase-js` |

Stary stack `https://api.bioteach.pl` jest poza tym kontraktem.

## Klient

Parametry RPC zachowują prefiks `p_`. Tożsamość i marka biorą się z JWT po bindzie.

```javascript
import { createClient } from "@supabase/supabase-js";

const supabase = createClient(
  "https://supabase-new.bioteach.pl",
  process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY,
);

const { data, error } = await supabase.rpc("get_chapter_catalog");
```

Edge wołasz przez `supabase.functions.invoke` (albo `fetch` na `/functions/v1/...`) z tym samym Bearer JWT. Dla `bind-session-brand` i `enroll-in-brand` przeglądarka musi wysłać nagłówek `Origin` — nie podstawiaj marki w body.

## Nazwy

OpenAPI używa **nowych** nazw RPC (`get_tasks`, `accept_legal`, `enroll-in-brand`, …). Nie ma starych aliasów. Rozdział zadania idzie z `task_requirement_mappings` → `requirement_positions.chapter_id` — nie ma tabeli `task_chapter_mappings`.
